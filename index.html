Jordan's Ticket Triage Assistant

Python · Streamlit · Claude API · 2026

An automated triage layer that sorts a support queue by urgency, with a plain-language reason attached, before an agent opens it. The system recommends. The agent always has the final say.

The problem

Jordan is a support rep handling 200–300 tickets a week. Every morning started with an unsorted queue and roughly 90 minutes of reading and re-ordering by hand. One week that cost a customer four hours on an unopened payment failure.

I started with five whys instead of code. The chain ended somewhere unexpected: the company already had years of labeled support data, it just wasn't being used to prioritize anything. The root cause wasn't Jordan working too slowly. It was a missing triage layer. That reframed the whole project: don't build a faster agent, build the sorted queue the agent should have been opening all along.

What the agent sees

Critical 92 Payment failed on renewal, account locked out breached
High 71 Production API returning 500s for all users 3.1h left
Medium 48 How do I export my report to PDF? 18h left
Low 29 Feature request: dark mode would be nice 60h left

How it's built

  1. Deterministic rule scorer. Every ticket gets a 0–100 urgency score and a category. No model in this path, so it's cheap and repeatable across 300 tickets.
  2. Critical-class safety net. Any ticket carrying a hard-priority signal (outage, breach, payment failed, locked out) is force-escalated to at least High regardless of its score. This is the single most important rule in the system, and it's covered by parametrized tests.
  3. Claude rationale layer. Explains the score in a bullet or two and suggests a queue. It explains the decision. It never re-makes it.
  4. Streamlit queue UI. Pre-sorted queue, per-ticket detail, and a confirm/adjust control that logs every agent override.

The scorer and the model are deliberately separate. If the API key is missing or a call fails, the batch job falls back to a deterministic rationale and the queue still sorts correctly. No single point of failure.

Results

Measured against the dataset's own ground-truth labels. No relabelling.

Evaluation metrics for the rule-based scorer
Top-severity recall the number that matters 49.2%
Tickets evaluated 11,923
Overall accuracy (3-way) 41.6%
Precision — high / medium 46.8% / 44.6%

Reading those numbers honestly

41.6% overall accuracy is not a good-looking number, and I'm not going to dress it up. Priority in this generic dataset is only weakly expressed through keywords, so a keyword scorer has a real ceiling. Most tickets labeled high contain no urgency vocabulary at all.

So the calibration optimizes recall on the top-severity class over overall accuracy, and trades high precision down on purpose. A missed critical ticket is Jordan's four-hour incident. A false alarm costs a glance. Those are not symmetric, and the metric shouldn't pretend they are.

Where the system is provably strong is the safety net: every ticket containing a hard-priority signal is guaranteed to escalate, and that guarantee is enforced by tests rather than by hope.

Unit Converter

Vanilla JS · Single file · 2026

A kilometer/mile converter that answers the question behind the question. Converting 42 km to 26.1 mi is arithmetic; knowing that's a marathon is the part a person actually wanted. It adds real-world scale context to every result.

Built as a single self-contained file with no dependencies and no build step. The constraint was the interesting part: every kilobyte had to earn its place, which is a useful way to find out how much of a typical front end is habit.

Approach

Find the real problem before writing code.

The triage project started as "help Jordan work faster" and ended as "the queue was never sorted." Those need completely different software. Five whys costs an afternoon and saves a rewrite.

Put the guarantee in a test, not in a promise.

The safety net is the most important rule in the triage system, so it's the most heavily tested thing in the repo. If a behavior matters, it should be impossible to break it quietly.

Report the number that's true, not the one that flatters.

I could have reported top-severity recall alone and looked better. The evaluation publishes overall accuracy, the full confusion matrix, and a limitations section, because a metric you can't argue with is worth more than one you can.

Let the model explain, not decide.

Scoring is deterministic and testable. The model writes the rationale. Keeping that boundary sharp is why the system still works correctly when the API is down.
